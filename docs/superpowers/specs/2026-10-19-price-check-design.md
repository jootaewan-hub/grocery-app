# 가격 확인 설계 (계획 ④)

2026-10-19 브레인스토밍. 화면 설계(`2026-10-16-screens-design.md`)의 4절(가격 출처와 표시 규칙), 5절(품목 상세), 7-1절(어떤 상품인지 정하기), 8-1절(확인이 언제 도는가)을 실제로 만드는 계획이다. 그 문서에서 정한 것은 다시 정하지 않고, 이 문서는 그 위에 이번에 정한 것과 범위를 적는다.

표시: [사용자] 사용자가 정함, [제안] 내 제안(사용자가 읽고 바꿀 수 있음), [빌더] 만드는 사람에게 맡김.

## 1. 왜

목록의 모든 줄에 "가격 확인 못 함"이 떠 있다. 사용자는 담기만 하면 앱이 알아서 가격과 주의사항을 찾아 두고, 품목을 누르면 그 내용이 보이기를 기대한다 [사용자]. 장보기 전에 "어디서 사면 얼마인지"와 "이 상품에 위반 기록이 있는지"를 한 화면에서 보는 것이 목적이다.

순서 [사용자, 2026-10-19]: 가계부 통합(D-008)보다 가격 확인을 먼저 하고, 이 저장소에 화면까지 완성한다. 서버 함수·테이블은 통합 때 그대로 쓰고, 화면은 가계부와 같은 디자인 체계(D-005)라 통합 때 옮긴다. status.md의 다음 할 일 순서를 이에 맞게 고친다.

## 2. 목표·비목표·실패 조건

목표
- 담는 순간 서버가 품목 이름으로 후보 상품을 찾기 시작한다 [사용자].
- 처음 한 번은 사용자가 후보 중 하나를 직접 고른다. 고른 상품은 가구 단위로 기억해, 같은 이름을 다시 담으면 고르지 않아도 그 상품으로 바로 가격을 찾는다 [사용자].
- 고르는 곳은 목록이다: 담기는 지금처럼 바로 끝나고, 목록 줄에 "후보 N개 찾음"과 "상품 고르기"가 붙는다(브라우저 시안 B안) [사용자].
- 포장 사진을 찍으면 제품명·용량을 읽어 그 상품으로 찾는다 [사용자].
- 품목을 누르면 가격(출처·확인 시각과 함께)과 주의사항(식품 API의 위반 기록)이 보인다 [사용자].
- 가격 출처는 이번에 모두 붙인다 [사용자: "이번에 다 하도록"]: 다나와, 에누리, 컬리·홈플러스·CJ더마켓 상품 페이지, 로우차트(쿠팡), 참가격. 자동으로 못 가져오는 곳은 바로가기 버튼, 그리고 "화면 캡처로 가격 넣기".

비목표(이번에 안 함)
- 품목 상세의 성분 탭과 대안 탭 [제안: 계획 ⑤로]. 이번에는 가격·안전·평가 탭과 요약 네 칸 중 세 칸(가장 싼 값, 식약처 기록, 평점)을 만들고, "더 나은 상품" 칸은 "다음 단계"로 비워 둔다.
- KAMIS 시세와 신선 품목 상세(계획 ③).
- 바코드로 상품 보기(매대 앞 바로 확인, 화면 설계 7절) [제안: 별도 계획].
- 가계부 내역에서 "우리가 산 값" 읽기 [제안: 지출 기록 계획과 함께].

실패 조건(돌아가도 실패로 본다)
- 출처·확인 시각 없는 가격, 모델이 추정한 가격, 검색 결과 발췌에 든 가격이 화면에 나온다.
- 용량·개수가 다른 상품의 가격을 같은 상품처럼 나란히 놓거나 "가장 싼 값"으로 뽑는다(예: 1.05kg 1개와 1.05kg×3개 묶음).
- robots.txt가 막은 경로나 약관이 자동 수집을 금지한 곳에서 가져온다.
- 다나와 검색을 10초에 한 번보다 자주 부른다(robots `Crawl-delay: 10`).
- 위반 기록이 검색되지 않았는데 "안전함"처럼 쓴다.

## 3. 제약

- CLAUDE.md의 "반드시 지킬 것" 전부: 출처 있는 숫자만, 기록 없음 ≠ 안전, 키는 서버에만, 가구 RLS, AI처럼 보이지 않게, 390·1280px 라이트·다크 캡처 확인, 외부 호출 한도와 캐시.
- 공유 DB는 `grocery` 스키마만 바꾼다(D-003). 적용은 Supabase MCP `apply_migration`, 사용자 확인 후.
- 외부 요청은 모두 Edge Function(서버)에서 한다. 실행 리전은 서울(`ap-northeast-2`)이고, 2026-10-19 임시 함수로 다나와 검색·상품 페이지가 막히지 않음을 확인했다(`docs/data-sources.md` 1-2-1).
- 같은 상품·같은 출처·같은 날은 다시 받지 않고 캐시를 돌려준다(화면 설계 8-1).

## 4. 흐름

### 4-1. 담기 → 후보 찾기 [사용자 + 제안]

1. 담기는 지금처럼 바로 목록에 넣는다.
2. 새 품목마다 서버가 후보를 찾는다. 가구가 같은 이름(용량 포함)으로 고른 적 있는 상품이 있으면 그 상품을 바로 잡고 4-3으로 간다.
3. 없으면 다나와 검색(`search.danawa.com/?query=품목 이름`)으로 후보를 받는다. 검색 결과 한 장에 상품 40개가 이름(용량 포함), 수량별 최저가, 100g당 가격과 함께 온다(2026-10-19 확인).
4. 다나와 검색은 전역으로 10초에 한 번만 보내도록 줄을 세운다. 두 사람이 한꺼번에 여러 품목을 담으면 차례로 처리하고, 그동안 목록 줄에는 "후보 찾는 중"을 쓴다 [제안].
5. 후보가 0개면 줄에 "후보를 찾지 못했어요"와 "사진으로 찾기"를 둔다.

### 4-2. 상품 고르기(목록에서) [사용자]

- 목록 줄: "후보 N개 찾음" + "상품 고르기" 버튼. 누르면 후보 시트가 열린다.
- 후보 시트: 상품 사진, 상품명, **용량·개수를 크게**, 다나와 최저가와 100g(또는 1개)당 가격(출처 "다나와"와 확인 시각). 묶음 구성(예: "왕교자 1.05kg×2 + 김치왕교자 420g×2")도 그대로 보여 주되 단품 후보를 위에 둔다 [제안: 순서는 빌더가 다듬는다].
- "사진으로 찾기"(4-4)와 "다시 검색"(사용자가 검색어를 고쳐 다시 찾기) [제안].
- 고르면 그 상품을 가구 기억에 저장하고 4-3을 시작한다. 바꾸기는 품목 상세에서 한다.
- 정육·수산·채소·과일(신선 품목)은 다나와에서 찾지 않는다 [사용자, 2026-10-19: "채소·과일 등은 다나와 말고 농수산물 가격 검색으로"]. 목록·상세에는 "농수산물 시세로 확인(준비 중)"을 쓰고, 시세(KAMIS 등)는 계획 ③에서 붙인다. (처음 제안한 "신선 품목도 다나와 후보를 고를 수 있다"를 대체한다.)

### 4-3. 가격 확인 [사용자: 모든 출처]

고른 상품 하나에 대해 서버가 출처마다 가격 줄을 모은다. 줄 하나 = 곳(판매처) + 값 + 배송비(있으면) + 출처 태그 + 확인 시각 + 수량.

| 출처 | 무엇을 읽나 | 상품 찾는 법 | 상태 |
|---|---|---|---|
| 다나와 | 상품 페이지 본문 "쇼핑몰별 최저가" 약 10줄(가격·배송비·몰 이름), JSON-LD 최저가·판매처 수·평점·후기 수 | 고른 후보의 pcode | 확인됨(2026-10-19) |
| 에누리 | JSON-LD 최저·최고가, 판매처 수 | 에누리 검색 또는 상품명 검색으로 같은 상품 찾기 | 확인 필요: 에누리 검색 경로의 robots, 같은 상품 맞추기 |
| 컬리 | 상품 페이지 JSON-LD `offers.price`, 후기 수 | 컬리 상품 주소를 찾는 방법 | 확인 필요: 컬리 검색이 서버 HTML로 오는지, 아니면 검색 API가 필요한지 |
| 홈플러스 | 상품 페이지 JSON-LD 가격(0이면 버림) | 같음 | 확인 필요: 검색 경로, 매장 유형별 가격 차이 |
| CJ더마켓 | JSON-LD 가격, `gtin13`(바코드) | 같음 | 확인 필요: 검색 경로 |
| 로우차트 | 쿠팡 상품의 현재가, 관측 최저·평균·최고가 | 로우차트는 `?keyword=` 검색이 robots 금지라, 쿠팡 상품 번호를 다른 방법으로 찾아야 한다 | 확인 필요(아래 7절) |
| 참가격 | 이마트·농협하나로·롯데슈퍼·GS더프레시 등 매장 가격, 조사일 | 공공데이터포털 API, 품목 대응표 | 사용자 할 일: 공공데이터포털 "한국소비자원_생필품 가격 정보" 키 신청 → Supabase Secrets에 넣기 |

규칙(화면 설계 4절 그대로)
- "가장 싼 값"은 **확인 시각이 오늘이고 고른 상품과 용량·개수가 같은 줄** 중에서 고른다. 참가격·로우차트 관측 최저처럼 과거 값은 비교 줄에만 나온다.
- 용량·개수가 다른 줄은 "다른 용량"으로 따로 묶고 100g(또는 1개)당 가격을 함께 쓴다.
- 다나와 상품 페이지는 기본 수량이 묶음일 수 있다(예: "1.05kg (3개)" 최저 27,650원, 같은 상품 1개는 검색 결과에서 10,380원). 수량을 맞춰 비교한다 [빌더: 수량 탭을 어떻게 읽을지].
- 출처 하나가 실패해도 나머지는 보여 주고, 실패한 출처는 "다나와 가격을 지금 불러오지 못했어요"처럼 적는다. 캐시 값을 보여 줄 때는 그 시각을 쓴다.
- 0원·음수는 버린다.
- 다른 출처의 상품이 고른 상품과 같은지 [사용자, 2026-10-19]: 브랜드·용량·개수가 모두 맞으면 앱이 자동으로 같은 상품으로 본다. 하나라도 애매하면 "같은 상품인지 확인 필요"로 따로 묶고 "가장 싼 값"에서 뺀다. 사용자가 한 번 "같은 상품 맞아요" 또는 "아니에요"를 누르면 그 출처의 연결을 가구 단위로 기억한다. 맞추는 기준(용량 표기 정규화 등)은 [빌더].
- 배송비 [제안, 내 결정]: 줄마다 배송비를 따로 적는다(모르면 "배송비 확인 못 함"). "가장 싼 값"은 상품 가격으로 고르고 그 줄의 배송비를 옆에 쓴다. 목록 합계는 상품 가격만 더하고 "배송비 제외"라고 적는다(배송비는 주문 단위라 품목마다 더하면 부풀려진다). "어디서 살지"의 온라인·매장 비교만 배송비를 포함한다(화면 설계 6절).

언제 도는가(화면 설계 8-1 그대로)
- 상품을 고르는 순간.
- 아직 사지 않은 품목은 하루 한 번 서버 정기 작업으로 다시 [제안: 식약처 동기화처럼 GitHub Actions 예약 실행 → Edge Function, 매일 07:30 한국 시간].
- 품목 상세를 열었는데 오늘 값이 없으면 그때.

### 4-4. 사진으로 찾기 [사용자]

- 후보 시트와 후보 0개 줄에서 "사진으로 찾기". 포장 앞면을 찍거나 고른다.
- 서버가 Claude로 제품명·브랜드·용량을 읽고, 사용자가 읽은 값을 확인·고친 뒤 그 값으로 다나와 검색을 다시 한다. 읽은 값은 검색어로만 쓰고 화면의 숫자로 쓰지 않는다.
- Claude 호출은 가계부 `extract-entries`와 같은 **WIF 방식**(로그인한 사용자의 Supabase JWT를 Anthropic 단기 토큰으로 교환, 저장할 API 키 없음)을 재사용한다 [사용자, 2026-10-19 결정 → D-009]. 모델·프롬프트는 [빌더](가계부는 사진 읽기에 Haiku 5.5, 어려운 경우 Sonnet 5.5). 같은 프로젝트 JWT로 가계부의 federation rule이 통과하는지는 첫 호출로 확인한다. 안 되면 [제안, 내 결정] 사진으로 찾기·캡처로 가격 넣기를 뒤로 미루고 나머지를 먼저 끝낸 뒤, federation rule 수정(사용자, Anthropic 콘솔)과 API 키 중 무엇으로 갈지 사용자에게 묻는다. 묻지 않고 API 키로 바꾸지 않는다.

### 4-5. 화면 캡처로 가격 넣기 [사용자]

- 품목 상세 가격 탭의 바로가기 옆. 쿠팡·이마트몰 같은 곳의 상품 화면을 캡처해 올리면 서버가 Claude(WIF)로 판매처·상품명·가격·용량을 읽는다.
- 읽은 값은 저장 전에 사용자가 확인한다. 저장하면 출처 태그 "캡처", 캡처 시각, 올린 사람과 함께 가격 줄이 된다. 오늘 캡처한 값은 "가장 싼 값" 후보가 될 수 있다 [제안].

### 4-6. 바로가기 [사용자]

- 자동으로 못 가져오는 곳(쿠팡, 이마트몰·SSG, 롯데ON, 오늘의집, 킴스클럽몰, G마켓 등)은 그 몰의 검색 결과 화면을 상품명으로 여는 버튼. 서버를 거치지 않고 새 창으로 연다.

## 5. 품목을 누르면 — 품목 상세 [사용자 + 화면 설계 5절]

화면 설계 5절의 구성을 따르되 이번 범위는 다음과 같다.

- 머리: 상품 사진, 상품명, 업체명, 분류, "상품 바꾸기".
- 요약 칸: 가장 싼 값 / 식약처 기록 / 평점 / 더 나은 상품("다음 단계").
- **가격 탭**: 4-3의 줄 목록(가장 싼 값부터), "다른 용량" 묶음, 바로가기, 화면 캡처로 가격 넣기.
- **안전 탭(주의사항)** [사용자: 식품 API에서 나온 위반 기록]:
  - 출처마다 확인 범위(어디까지 등록분, 마지막 동기화 시각)와 결과. 기록이 없으면 "확인한 범위에서 찾은 기록 없음".
  - 이번 범위의 출처: I0490 회수·판매중지, I2620 검사부적합(업체 기록), I2715 해외직구 위해식품, **I2810 해외 위해식품 회수**(새로 매일 수집, 538건 규모) [제안]. I0470 행정처분은 업소 단위라 상품과 인허가번호로 이어질 때만 쓰는데, 다나와 상품에는 인허가번호가 없어 이번에는 넣지 않는다 [제안].
  - 목록과 상세는 같은 결과를 쓴다 [제안, 내 결정]: 상품을 고른 뒤에도 품목 이름으로 맞춘 기록을 버리지 않고, 고른 상품명·업체명으로 맞춘 기록을 더한다(합집합). 놓치는 쪽이 더 위험하다(화면 설계 8-2). 상세에는 기록마다 "품목 이름으로 찾음 / 상품명으로 찾음"을 적어, 목록에 경고가 있는데 상세가 "찾은 기록 없음"인 모순이 생기지 않게 한다.
  - 상품명 대조는 고른 상품의 정확한 상품명·업체명으로 한다(지금 목록의 "비슷한 기록" 규칙과 같은 방식, 품목 이름보다 정확함). 다나와 상품에는 바코드·품목보고번호가 없어 "같은 상품 기록(바코드 일치)"은 CJ더마켓 `gtin13`처럼 바코드를 얻은 경우에만 가능하다 [제안: 바코드가 있으면 바코드 일치를 먼저 본다].
  - 농가 단위 농산물 부적합(I2620 중 생산자 이름 가림·미상·불가·불명)은 목록에서는 숨기지만(2026-10-19 결정), 품목 상세 안전 탭에서는 "같은 품목 농산물 부적합 N건(농가 단위)"으로 보여 준다 [제안: 사용자가 "목록에서는 숨기기"를 골랐고, 상세에서 볼 수 있게 하자는 게 그때의 설명이었다].
- **평가 탭**: 다나와 평점·후기 수(출처, 기준일), 컬리 후기 수, "원래 페이지에서 후기 보기". 후기 본문은 복제·요약하지 않는다.

## 6. 목록에 생기는 변화 [화면 설계 6절]

- 줄 오른쪽: 오늘 찾은 최저가와 곳(예: "10,380원 11번가"). 못 찾았으면 지금처럼 "가격 확인 못 함".
- 줄 둘째 줄: "상품 고르기 전 · 후보 N개 찾음" / "후보 찾는 중" / 고른 상품명.
- 요약의 "찾은 최저가 합계"와 "확인 못 함" 개수가 채워진다. 합계는 개수(×N)를 곱한다 [제안].
- "어디서 살지" 보기: 온라인 최저가(배송비 포함)와 참가격 매장 가격이 둘 다 있을 때만 "온라인이 더 싼 것"을 판단한다. 매장은 설정의 "자주 가는 매장"(기본: 성남시 분당구 근처 참가격 조사 판매점) [화면 설계 7-2].
- 진행 표시는 하는 일 그대로: "다나와 가격 확인 중", "후보 찾는 중".

## 7. 확인 필요 (코드 전에 실제 호출로 확인하고 data-sources.md를 고친다)

1. 에누리·컬리·홈플러스·CJ더마켓에서 **상품 주소를 찾는 방법**: 각 사이트 검색 화면이 robots 허용이고 서버 HTML로 오는지. 안 되면 그 출처는 다나와 상품명으로 검색 API(Exa 등)를 써서 상품 페이지 주소만 찾는다(가격은 페이지에서 직접 읽는다). 검색 API 키가 필요하면 사용자에게 묻는다.
2. **쿠팡 상품 번호 찾기**(로우차트용): 로우차트 검색은 robots 금지. 다나와 판매처 목록에 쿠팡이 나오면 그 링크, 아니면 검색 API로 쿠팡 상품 주소를 찾는 방법.
3. 각 몰 약관의 자동 수집 조항(다나와 제24조② "영리목적 복제 금지" 등). 이 앱은 비상업·두 사람 사용이지만 법적 판단은 아니다.
4. 참가격 API 실제 응답(판매점별 가격, 조사일), 분당구 근처 조사 판매점, 품목 대응 방법.
5. 다나와 수량 탭(1개·2개·3개…)별 가격을 상품 페이지에서 읽을 수 있는지, 아니면 검색 결과의 수량별 가격만 쓸 수 있는지.
6. WIF: 장보기 함수에서 가계부의 federation rule로 토큰 교환이 되는지.
7. I2810 활용신청(사용자, 식품안전나라).

## 8. 만드는 사람에게 맡기는 것 [빌더]

- 테이블 설계(예: 상품, 가구별 상품 기억, 후보, 가격 줄 캐시), Edge Function 나누기, 다나와 요청 줄 세우기 구현.
- HTML 파싱 방법. 다나와 검색 결과는 Tailwind 클래스라 구조가 바뀌면 깨지기 쉬우므로, 파싱 실패를 "가격 확인 못 함 + 출처 오류"로 드러내고 테스트용 HTML 사본(fixture)으로 시험한다.
- 후보 정렬(단품 우선 등), "다시 검색" 화면, 품목 상세의 세부 배치(가계부 디자인 체계, 1280px 넓은 화면).
- 사진·캡처 읽기의 모델과 프롬프트, 이미지 크기 제한.
